## Notes on individual decisions

**ADR-0002 rationale.** The blueprint's "Employment #1 / #2" is satisfied today by lifecycle spells on one Employee; splitting employees per spell would duplicate identity and break the lifetime record. A future `employments` table is additive (`employee_positions.employment_id`) if separate contracts must carry separate codes or legal entities.

**ADR-0004 rationale for manager visibility.** A manager who cannot see a direct report cannot approve, review or coach; reporting relationships are audited, effective-dated and set by HR, so they are a safe basis for access. Indirect reports are intentionally not included by default.

**ADR-0005 rationale.** A generic field matrix would duplicate the permission catalogue; classification in config plus per-model masking is testable and sufficient until a tenant needs per-field configuration.

**ADR-0013 rationale.** Interface + middleware is the smallest mechanically enforceable pattern: the architecture test checks every `ShouldQueue` class in `app/`, so a new job cannot be merged without carrying its tenant.

**ADR-0014 API-key scope.** Data contract: `api_keys.access_scope` JSON nullable with the same shape as `user_access_scopes` grouped by dimension; enforcement: `AuthenticateApiKey` registers a synthetic principal in `AccessScopes` so the same global scope applies. Not built now because no consumer needs it before the Integration Hub.

## SaaS.1 proposed decisions

Recorded by SaaS.1 (Commercial Architecture & Gap Analysis, 6 October 2026). Status **Proposed (SaaS.1)** means the architecture is agreed for planning and no code exists. Each decision becomes **Accepted** when the workstream that implements it lands, with the enforcement listed below. The narrative and reasoning are in `docs/saas/` (start with `SaaS-1-Commercial-Architecture-Gap-Analysis.md`).

| ADR | Title | Status | Decision (one line) | Enforced by (planned) |
|---|---|---|---|---|
| 0017 | Commercial layer placement & record ownership | Proposed (SaaS.1) | Commercial bounded contexts (`app/Domain/Commercial/{Catalog, Entitlements, Subscriptions, Billing, Tax, Metering}`) live inside the modular monolith and its database, not a separate service, so count limits commit in the HCM write's transaction; commercial records are platform-owned and tenant-keyed (no `BelongsToTenant`, the `AuditEvent` precedent), read only through commercial services and the tenant billing read model; opaque ULID references outside the database | Architecture tests: commercial model reads confined to commercial services; no HCM module imports commercial internals |
| 0018 | Entitlement contract | Proposed (SaaS.1) | `allowed = AccessMode ∧ Entitlement ∧ OperationalFlag ∧ Limit`, beneath permission, scope and field security and never widening them; HCM depends only on the `Entitlements` contract; capabilities are code-owned in `config/peopleos.php`; plan terms, add-ons and overrides compile into effective-dated, hashed snapshots; security controls are never entitlements | `Entitlements` contract; module filter in `User::permissionKeys`; architecture test that HCM never reads plans or subscriptions |
| 0019 | Commercial system of record & payment providers | Proposed (SaaS.1) | PeopleOS owns subscriptions, invoices, credit notes, tax and the billing ledger and issues its own GST invoices; providers are adapters behind `PaymentGateway`; provider webhooks enter a platform-level, verified, idempotent `billing_provider_events` pipeline (not tenant `inbound_events`); money in integer minor units; no card data ever | `PaymentGateway` contract tests; unique provider event id; signature verification tests |
| 0020 | Separate tenant lifecycle and subscription state machines | Proposed (SaaS.1) | Tenant lifecycle (Platform) and subscription (Commercial) are separate machines with append-only transition rows; access mode (`full`, `grace`, `restricted`, `locked`, `none`) is derived by one service and checked at every entry point; `trial` moves from tenant status to the subscription; commercial events never set tenant `suspended` directly | Transition-table tests; access-mode checks in `ResolveTenant`, download routes, `AuthenticateApiKey`, `BindTenantContext`, `TenantRunner` |
| 0021 | Plan versioning & grandfathering | Proposed (SaaS.1) | Published plan versions are immutable; subscription items pin a version; a new version reaches existing customers only through an explicit, announced plan migration at a renewal boundary; nothing retroactive | Immutability guard on published versions; plan-migration tests |
| 0022 | Count limits at domain choke points | Proposed (SaaS.1) | Count limits are checked in-transaction under a lock where the count changes; `employees.active` in `LifecycleEngine::transition()` (the sole writer of employment state); one canonical `BillableUnits` definition; counts sampled from HCM tables, consumption metered as usage events; MySQL authoritative, Redis never | MySQL concurrency suite ("concurrent employee creation cannot exceed limit"); enforcement-matrix tests per path |
| 0023 | Commercial tax separate from statutory compliance | Proposed (SaaS.1) | GST on PeopleOS's own invoices is a Tax context with its own tables, rules and a pure `TaxCalculator`; never mixed with statutory payroll compliance; unverified tax rules cannot finalise an invoice | Architecture test (no cross-imports); verified-rule gate tests |
| 0024 | No second audit or event system | Proposed (SaaS.1) | Commercial "why" questions are answered by append-only transition tables plus `AuditRecorder` events with correlation ids; operator and tenant-lifecycle actions are recorded on the platform chain; no generic `CommercialEvent` log | Audit tests for every platform action; chain verifier covers commercial actions |
| 0025 | Tenant deletion & the audit exception | Proposed (SaaS.1) | Tenant deletion is an ordered per-domain purge with cooling-off, legal hold, dual control and a deletion certificate, never a blind cascade; the tenant's own audit chain is purged last as the only sanctioned exception to "audit is never purged", recorded on the platform chain; Markedge's commercial and tax records are retained | Deletion workflow tests (cancel, hold, execute, residual-row and file checks) |
| 0026 | Commercial enforcement rollout | Proposed (SaaS.1) | Existing tenants are backfilled onto a private "Legacy" plan equal to today's behaviour; `commercial.enforcement` per capability moves `off` → `observe` (log would-refuse, refuse nothing) → `enforce` only after zero false refusals are observed | Observe-mode tests; backfill test (every tenant has a subscription and snapshot); existing tests unchanged |

**Why these are proposals, not decisions in force.** SaaS.1 was discovery and architecture only. Product, finance and legal decisions (D-1 to D-17 in the gap analysis §26) can still change pricing, trials and retention, but none of them changes these structural choices.

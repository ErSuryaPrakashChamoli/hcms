## Notes on individual decisions

**ADR-0002 rationale.** The blueprint's "Employment #1 / #2" is satisfied today by lifecycle spells on one Employee; splitting employees per spell would duplicate identity and break the lifetime record. A future `employments` table is additive (`employee_positions.employment_id`) if separate contracts must carry separate codes or legal entities.

**ADR-0004 rationale for manager visibility.** A manager who cannot see a direct report cannot approve, review or coach; reporting relationships are audited, effective-dated and set by HR, so they are a safe basis for access. Indirect reports are intentionally not included by default.

**ADR-0005 rationale.** A generic field matrix would duplicate the permission catalogue; classification in config plus per-model masking is testable and sufficient until a tenant needs per-field configuration.

**ADR-0013 rationale.** Interface + middleware is the smallest mechanically enforceable pattern: the architecture test checks every `ShouldQueue` class in `app/`, so a new job cannot be merged without carrying its tenant.

**ADR-0014 API-key scope.** Data contract: `api_keys.access_scope` JSON nullable with the same shape as `user_access_scopes` grouped by dimension; enforcement: `AuthenticateApiKey` registers a synthetic principal in `AccessScopes` so the same global scope applies. Not built now because no consumer needs it before the Integration Hub.

## SaaS.4 decisions

Recorded by SaaS.4 (Commercial Plan Foundation, 6 October 2026). Status **Accepted (shadow)**: in force for plans and plan assignments; nothing is enforced. Report: `docs/saas/SaaS-4-Commercial-Plan-Report.md`.

What happens to the earlier proposals:
- Proposed **ADR-0021** (plan versioning and grandfathering) is implemented for immutable published versions and for assignments pinned to a version. It stays **Proposed** for plan migrations, which belong to subscriptions.
- Proposed **ADR-0026** (Legacy-plan backfill) is **not** implemented: no plan is created or assigned by default.
- Proposed **ADR-0017** (platform-owned commercial records) applies to the plan catalogue, which has no tenant. It stays open for billing records.

| ADR | Title | Status | Decision (one line) | Enforced by |
|---|---|---|---|---|
| 0031 | Plan catalogue: stable plans, immutable versions | Accepted (shadow) | `plans` (permanent code, name, description) and `plan_versions` (`draft → published → retired`, the ADR-0009 `VersionStatus`) are platform-level, without a tenant. *Scheduled*, *active* and *superseded* are derived from the sale window, never stored. Publishing ends the previous version's sale the day before; retiring stops new assignments. Plans reference capabilities of the code-owned catalogue and never redefine them. Only platform operators change plans, with a reason, audited on the platform chain | `PlanCatalogTest`, `ArchitectureTest`, `PlanConcurrencyTest` |
| 0032 | Tenant plan assignment is effective-dated tenant configuration | Accepted (shadow) | `tenant_plan_assignments` (`BelongsToTenant`, ADR-0027) pins a published version for an inclusive date range. Rules: one assignment per day (painted like configuration rows: the earlier one ends, a future one is cancelled, a longer one resumes after); today or later; inside the version's sale window. Only platform operators assign, with a reason, under the tenant's profile lock, audited on both chains with the previous plan, the new plan and the effective date. The catalogue changing (new version, retirement) never moves an assigned tenant. No tenant is assigned by default | `PlanAssignmentTest`, `PlanSecurityTest`, `PlanConcurrencyTest` |
| 0033 | The plan is a layer of the existing engine | Accepted (shadow) | Precedence: catalogue → override → the tenant's own configuration row → **plan** → configured-without-row (SaaS.3) → UNKNOWN. Pinned versions are cached inside the tenant's state with no catalogue invalidation, because they are immutable. A tenant that never had a plan reads exactly as in SaaS.3 (`has_plan_assignments` marker) | `PlanAssignmentTest`, `PlanPerformanceTest`, `EntitlementEngineTest` (unchanged) |
| 0034 | Plans never switch a protected capability off | Accepted (shadow) | A plan may include a protected capability (payroll, onboarding, exit, `active_employees.max`) or leave it out ("not sold"). Per-tenant configuration and overrides keep their SaaS.3 behaviour (an explicit, reasoned decision for one tenant) | `PlanCatalogTest` |

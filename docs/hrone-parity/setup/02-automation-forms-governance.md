Prepared 2026-10-28, read-only. HROne input: the extracted Setup templates (`spec/02_Automation.md`, `spec/03_Forms_templates.md`, `spec/04_Governance.md`, `spec/common-settings-automation.md`) and the captured page text (`setup/02_*.txt`, `03_*.txt`, `04_*.txt`, which list the rows, options and tabs the templates do not show). PeopleOS evidence: the code on branch `feature/oct_22_salary_module` (working tree), paths relative to `/home/administrator/Documents/hrms/hcms`.

**Status key.** HAVE = PeopleOS configures and enforces it. PARTIAL = something exists but not the whole HROne control, or it exists but is not configurable or not enforced. MISSING = nothing equivalent. N-A = not applicable, with the reason given. Generic dialog chrome ("clear", "Next", "Cancel", loaders, avatars) is ignored.

**Out of scope.** Recruitment rows are N-A (separate RMS behind `POST /api/v1/pre-employees`). The other modules' panels inside HROne's shared Settings drawer (time office, payroll, helpdesk, timesheet, engage points, performance, asset, expense) are covered by the other section files. This file covers only the drawer's own controls ("Delete transaction") and the task-settings panel (`app-task-setting`).

**Existing gap IDs referenced:** `docs/hrone-parity/HROne-Gap-Register.md`: IP-01 (delegation), IP-02 (bulk approval), IP-03 (discussion/archive), IP-04 (business partners), IP-07 (channels), WF-01..WF-11, CF-16..CF-22.

## Notable findings from reading the code

1. **The password expiry setting is not enforced.** → fixed (HS-P1): `EnforceAccountSecurity` sends expired password sessions to `ChangeExpiredPassword`. `security.password_expiry_days` is offered in Setup → Governance and on `app/Filament/Pages/SecurityPolicyPage.php`. `SecurityPolicy::passwordExpired()` (`app/Domain/Enterprise/Services/SecurityPolicy.php:69`) is never called anywhere in `app/`, `routes/` or `bootstrap/`. An admin who sets "Expire after 90 days" gets no effect. This breaks the Setup-centre rule that a setting is listed only when code reads it.
2. **Two security defaults are never read.** → removed (HS-P1). `security.password.min_length` (12) and `security.session.lifetime_minutes` (120) are declared in `config/peopleos.php` `settings` (lines 867–868) and not read anywhere. The live keys are `security.password_min_length` (10) and `security.session_idle_minutes`.
3. **The workflow `document` node is a stub.** → fixed (HS-P5): the node writes a letter from a chosen template for the run's employee (`WorkflowEngine::generateDocument`, optionally issued at once); a node without a template is skipped as before. `WorkflowEngine::execute` logs "skipped … arrives with the Letter Factory" (`app/Domain/Workflow/Services/WorkflowEngine.php:201`). So no letter is generated by a process, even though the letter studio now exists.
4. **Loans, reimbursement claims and variable pay emit no domain events.** → fixed (HS-P5): `payroll.loan_requested/approved/rejected/disbursed`, `payroll.claim_submitted/approved/rejected/paid`, `payroll.variable_pay_requested/approved/rejected` (PayrollEvent; in `notifications.events`; the "requested" ones are workflow triggers). `app/Domain/Loans`, `app/Domain/Claims` and the variable pay services dispatch nothing. As a result they cannot trigger notification rules or workflows, and they appear in no notification catalogue.
5. **A per-node approver fallback (HROne's "reliever") exists in the engine but has no UI.** → builder field added (HS-P14). `WorkflowEngine::createTask` reads `config.fallback`, but `app/Filament/Support/WorkflowBuilderSchema.php` has no field for it.
6. **Requests that cannot be routed through a configurable workflow.** → imports routable (HS-P2: trigger `import.validated`, `ImportWorkflowBridge`); → the others routable (HS-P5: regularisations, loans, claims, variable pay, compensation changes, letters, resignations and investment declarations, each with a `WorkflowCompleted` bridge; `RequestWorkflows` says when a run decides its request). Attendance regularisations, loans, claims, variable pay, compensation changes, letters, resignations and imports each have a fixed approval. Only leave, time-office, location, donation and encashment requests, service-desk requests (which include profile changes), workforce plans, surveys, learning and succession have `WorkflowCompleted` bridges (`app/Providers/AppServiceProvider.php:546-554`, `app/Providers/ParityServiceProvider.php:115-118`).
